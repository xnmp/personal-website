<!-- block: headline -->
A gothic dungeon crawler where nearly every asset comes out of a script.

<!-- block: an-original-first-person-game-for-unreal-engine-5 -->
An original first-person game for Unreal Engine 5.8.2, inspired by the cathedral descent in Diablo 1. You start in a village called Greyhollow, walk into the church, go down through the nave and two burial crypts, and fight the Butcher.

<!-- block: it-is-paused-as-a-work-in-progress -->
It is paused as a work in progress. The part I would defend is the structure underneath: rules without an engine, and art without a mouse.

Game rules that compile without Unreal

<!-- block: seven-headers-in-source-ashencathedral-domain-871-lines-co -->
Seven headers in `Source/AshenCathedral/Domain/`, 871 lines counted with `wc -l`.

<!-- block: combat-resources-items-trading-abilities-enemy-stats-the-t -->
Combat, resources, items, trading, abilities, enemy stats, the town map and exploration are plain C++17 headers with no engine includes. The Unreal actors call into them. Damage and wind-up for the Butcher come from `enemyDamage` and `enemyWindup` in `Rules.h`, and the actor only decides when to ask for the enraged numbers.

<!-- block: that-split-is-what-makes-the-tests-cheap -->
That split is what makes the tests cheap. `Scripts/test_rules.sh` compiles eight test programs with `clang++ -Werror` and AddressSanitizer plus UndefinedBehaviorSanitizer, then runs five Python unittest files for the asset pipeline. No editor, no GPU.

FIG. 1 · one of eight sanitizer runs

<!-- block: caption-from-scripts-test-rules-sh-the-other-seven-follow -->
From Scripts/test_rules.sh. The other seven follow the same pattern for items, trade, enemies, exploration, town map, abilities and UI geometry.

<!-- block: code-clang-std-c-17-wall-wextra-werror-fsanitize-address-u -->
```
clang++ -std=c++17 -Wall -Wextra -Werror \
  -fsanitize=address,undefined \
  Tests/RulesTests.cpp -o Saved/Tests/rules
ASAN_OPTIONS=detect_leaks=0 Saved/Tests/rules
```

<!-- block: the-tests-include-hostile-input -->
The tests include hostile input. `Tests/ExplorationTests.cpp` checks that line of sight from `INT_MIN` to `INT_MAX` returns false and that a radius of `INT_MAX` returns nothing. I put those in after deciding the fog-of-war code should never trust its coordinates.

Assets generated from code

<!-- block: scripts-has-12-generate -->
`Scripts/` has 12 `generate_*.py` files and a set of `prepare_*` and `import_*` steps behind them.

<!-- block: props-the-reliquary-the-gate-the-town-and-several-characte -->
Props, the reliquary, the gate, the town and several character candidates are written as Blender Python. Importers then build materials, meshes, skeletal enemies, animation clips and the Cathedral map inside Unreal. If an asset looks wrong I change a script and re-run it.

<!-- block: the-butcher-shows-how-this-goes -->
The Butcher shows how this goes. `SM_Butcher` was a procedural figure built from primitives, and it looked like it. The replacement starts from CC0 MakeHuman anatomy and goes through `Scripts/revise_butcher_detail.py` and `export_baked_butcher.py`, which bake the materials down for Unreal. `Docs/ART.md` records which source assets are replacements and which are legacy.

<!-- block: my-gpu-fell-off-the-bus-so-the-agents-got-limits -->
My GPU fell off the bus, so the agents got limits

<!-- block: sources-docs-gpu-incident -->
Sources: `Docs/GPU_INCIDENT.md` and `Docs/RESOURCE_LIMITS.md`.

<!-- block: on-7-september-2026-while-a-packaged-native-build-was-runn -->
On 7 September 2026, while a packaged native build was running, the kernel log recorded NVIDIA Xid 79, “GPU has fallen off the bus.” Unreal logged `VK_ERROR_DEVICE_LOST` three seconds later and the display driver failed every query until the machine restarted, about two minutes after the Xid.

<!-- block: the-cause-is-still-open -->
The cause is still open. No temperature history existed, the log window showed no thermal or PCIe error beforehand, and the Unreal breadcrumb pointed at a buffer upload, which does not say much. The incident note says in so many words that it does not establish overheating and does not prove Lumen was to blame.

<!-- block: what-i-could-do-was-reduce-the-load-and-record-better-evid -->
What I could do was reduce the load and record better evidence. Heavy work now goes through `Scripts/resource_guard.py`, which runs it in a systemd user service with a 400% CPU quota, checks that quota before starting, allows one heavy job at a time, and polls temperature and memory every five seconds. If telemetry is missing it refuses to start. Unreal gets `-corelimit=3` and Blender gets four threads on CPU rendering. Previews are capped at 30 fps and 67% resolution.

<!-- block: it-was-tested-20-lightweight-guard-tests-passed-on-23-sept -->
It was tested: 20 lightweight guard tests passed on 23 September, and on 25 September three back-to-back Blender previews plus an indexer pushed the CPU to 88.5 °C and the guard stopped the job. Neither document claims the GPU fault is fixed, and GPU playtests stay stopped except for short guarded captures I authorised on 25 September.
